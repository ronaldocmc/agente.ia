8. Como implementar agentes: laboratórios progressivos

Nesta seção, vamos transformar os conceitos em experiências práticas.

O objetivo não é utilizar todas as tecnologias ao mesmo tempo, mas compreender o que cada recurso acrescenta à arquitetura.

8.1 Laboratório 1 — Automação determinística sem LLM #

Problema: identificar produtos que precisam de reposição.

Tecnologias: Python e dados fictícios.

O agente recebe estoque atual, venda média diária, prazo de entrega e estoque de segurança.

O ponto de pedido simplificado é:

\[ PP=(D\times LT)+ES \]

Em que:

  • \(PP\): ponto de pedido;
  • \(D\): demanda média diária;
  • \(LT\): prazo de reposição em dias;
  • \(ES\): estoque de segurança.

Exemplo:

def avaliar_reposicao(estoque_atual, venda_media_dia, prazo_entrega, estoque_seguranca):
    ponto_pedido = venda_media_dia * prazo_entrega + estoque_seguranca
    return {
        "ponto_pedido": ponto_pedido,
        "estoque_atual": estoque_atual,
        "repor": estoque_atual <= ponto_pedido,
    }

resultado = avaliar_reposicao(21, 4, 5, 6)
print(resultado)

Nesse caso, o ponto de pedido é 26 unidades, portanto o sistema recomenda avaliar uma reposição.

Não foi utilizado um LLM.

A decisão é baseada em uma regra explícita, adequada como solução inicial e baseline.

8.2 Laboratório 2 — Orquestração determinística #

Problema: consolidar análises de estoque e finanças antes de recomendar uma compra.

Podemos criar funções especializadas e um coordenador.

def agente_estoque():
    return {"produto": "Produto A", "necessita_reposicao": True, "custo_estimado": 1200}


def agente_financeiro():
    return {"saldo_disponivel": 3000}


def orquestrar():
    estoque = agente_estoque()
    financeiro = agente_financeiro()
    pode_comprar = (estoque["necessita_reposicao"] and
                   financeiro["saldo_disponivel"] >= estoque["custo_estimado"])
    return {
        "estoque": estoque,
        "financeiro": financeiro,
        "compra_financeiramente_viavel": pode_comprar,
        "aprovacao_humana_necessaria": True,
    }

print(orquestrar())

Esse exemplo demonstra que a orquestração pode acontecer inteiramente em Python, sem LLM.

A viabilidade financeira não representa autorização para efetuar a compra.

8.3 Laboratório 3 — Classificação de mensagens de CRM #

Problema: identificar o assunto principal de uma solicitação recebida.

Uma primeira implementação pode utilizar regras.

def classificar_mensagem(mensagem):
    texto = mensagem.lower()
    if "devolução" in texto or "troca" in texto:
        return "pos_venda"
    if "boleto" in texto or "pagamento" in texto:
        return "financeiro"
    if "preço" in texto or "comprar" in texto:
        return "vendas"
    return "revisao_humana"

mensagem = "Gostaria de saber o preço do produto"
print(classificar_mensagem(mensagem))

Essa solução é limitada por sua dependência de palavras-chave.

Um experimento posterior pode comparar regras, TF-IDF, classificadores tradicionais e LLMs.

O importante é medir se a inclusão do modelo melhora efetivamente os resultados.

8.4 Laboratório 4 — Introdução ao RAG #

Problema: recuperar informações sobre políticas institucionais.

Antes de implementar embeddings, podemos construir uma recuperação lexical simples.

documentos = [
    {"id": 1, "texto": "A publicação exige revisão editorial."},
    {"id": 2, "texto": "Registros duplicados devem ser identificados."},
    {"id": 3, "texto": "Notícias precisam possuir fonte verificável."},
]


def recuperar(termo):
    termo = termo.lower()
    return [doc for doc in documentos if termo in doc["texto"].lower()]

print(recuperar("fonte"))

Esse exemplo demonstra apenas recuperação lexical. Não constitui um sistema RAG completo, pois não contém geração fundamentada por um modelo.

O próximo passo seria implementar embeddings, indexação vetorial, recuperação híbrida e geração com citações.

8.5 Laboratório 5 — Registro de ferramentas #

Problema: oferecer operações específicas para utilização por agentes.

def consultar_estoque(produto_id):
    estoques = {1: 20, 2: 5, 3: 42}
    return estoques.get(produto_id)

ferramentas = {"consultar_estoque": consultar_estoque}


def executar_ferramenta(nome, argumentos):
    if nome not in ferramentas:
        raise ValueError("Ferramenta não autorizada")
    return ferramentas[nome](**argumentos)

resultado = executar_ferramenta("consultar_estoque", {"produto_id": 2})
print(resultado)

Esse exemplo demonstra um registro simples de ferramentas.

Em sistemas reais, devemos incluir validação de parâmetros, autenticação, controle de permissões, tratamento de exceções e auditoria.

8.6 Laboratório 6 — Disponibilizar ferramentas por API #

Tecnologia: FastAPI.

Uma ferramenta pode ser exposta por meio de uma API REST.

from fastapi import FastAPI

app = FastAPI()


@app.get("/estoque/{produto_id}")
def consultar_estoque(produto_id: int):
    estoques = {1: 20, 2: 5, 3: 42}
    return {"produto_id": produto_id, "estoque": estoques.get(produto_id)}

Após salvar o arquivo como api.py, instalar as dependências e executar:

pip install fastapi uvicorn
uvicorn api:app --reload

A documentação interativa ficará disponível localmente em:

http://127.0.0.1:8000/docs

Essa API pode ser utilizada por n8n, agentes ou aplicações externas autorizadas.

O exemplo não possui autenticação e não deve ser publicado diretamente em produção.

8.7 Laboratório 7 — Integração com n8n #

Agora podemos construir um workflow que consome a API criada.

O fluxo didático será:

Manual Trigger → HTTP Request → If → Formatar Resultado → Notificação Simulada

O primeiro nó inicia o processo. O segundo consulta a API. O nó condicional verifica o resultado e encaminha a execução.

Depois, podemos substituir o início manual por um agendamento.

O experimento deve comparar duas versões: uma puramente determinística e outra com um agente de IA responsável por uma subtarefa que exija interpretação ou seleção dinâmica de ferramentas.

8.8 Laboratório 8 — Agente utilizando OpenAI Agents SDK #

O SDK permite definir agentes, instruções e ferramentas.

Exemplo conceitual, sujeito à API da versão instalada:

from agents import Agent, Runner, function_tool


@function_tool
def consultar_estoque(produto_id: int) -> dict:
    """Consulta estoque fictício de um produto."""
    return {"produto_id": produto_id, "estoque": 12}


agente = Agent(
    name="Analista de Estoque",
    instructions="Consulte ferramentas quando necessário. Não realize compras.",
    tools=[consultar_estoque],
)
# Execução exige SDK instalado, credenciais e modelo configurados.
# Ex.: resultado = Runner.run_sync(agente, "Verifique o estoque do produto 1")

Depois, utilizando um ambiente devidamente configurado, podemos solicitar que o agente consulte um produto.

O aspecto fundamental é observar o ciclo:

Solicitação → decisão de ferramenta → validação → execução → resultado → resposta.

Os alunos também devem estudar os exemplos oficiais de handoff e agentes como ferramentas.

8.9 Laboratório 9 — Google ADK #

Utilizar uma receita oficial simples como ponto de partida.

O objetivo é desenvolver um agente coordenador que recebe uma solicitação e seleciona especialistas.

Exemplo aplicado ao CRM:

Coordenador → Agente de Vendas / Agente Financeiro / Agente de Suporte → Consolidação

É importante documentar como ocorre o roteamento, quais informações são compartilhadas e como erros são tratados.

8.10 Laboratório 10 — Claude Agent SDK #

O experimento inicial deve utilizar um diretório isolado.

O agente recebe a solicitação de analisar arquivos de teste e produzir um relatório.

Na primeira execução, devem ser disponibilizadas apenas ferramentas de leitura.

Posteriormente, pode-se permitir escrita em uma pasta temporária.

O objetivo é estudar controle de permissões e segurança da execução.

8.11 Laboratório 11 — LangGraph #

O problema será implementar uma análise comercial com controle explícito de estado.

O grafo poderá conter os nós:

coletar_dados → validar → analisar → autorizar → registrar

Cada nó possui uma responsabilidade.

O experimento deve incluir interrupção, falha simulada e retomada.

Na versão agêntica, um modelo poderá selecionar análises complementares, sem contornar as etapas obrigatórias de validação e autorização.

8.12 Laboratório 12 — CrewAI #

Primeiro devemos desenvolver uma solução de agente único.

Depois, implementar uma equipe especializada:

  • Agente de estoque;
  • Agente de vendas;
  • Agente financeiro.

O problema, os dados e as ferramentas devem permanecer equivalentes.

A avaliação deve verificar se a divisão entre agentes realmente melhora a qualidade da solução e quanto aumenta custo, latência e complexidade.

8.13 Laboratório 13 — MCP e skills #

O objetivo é combinar interoperabilidade e conhecimento procedural.

O experimento envolve criar uma função de consulta de estoque, disponibilizá-la por um servidor MCP e construir uma skill que descreva como elaborar um relatório.

Em seguida, comparar três abordagens:

Ferramenta diretamente registrada no SDK, ferramenta exposta por MCP e skill que orienta a utilização das ferramentas.

Devemos verificar como cada abordagem influencia reutilização, manutenção, segurança e interoperabilidade.

8.14 Laboratório 14 — OpenClaw e Hermes #

O objetivo é experimentar ambientes agênticos com recursos prontos.

O agente deve inicialmente trabalhar apenas com dados sintéticos e ferramentas limitadas.

Uma atividade possível é consultar documentos locais, identificar informações e preparar um relatório.

É importante verificar quais recursos são utilizados, que permissões foram concedidas e quais ações foram efetivamente realizadas.

Não se recomenda iniciar os testes com acesso irrestrito ao sistema operacional, e-mail real ou contas institucionais.
