23. Guia de decisão e projetos integradores

23.1 Se a dúvida for «o que usar para construir meu primeiro agente?» #

  1. Especificar o problema, ambiente, política de ação e dados.
  2. Implementar uma referência determinística em Python.
  3. Introduzir um modelo de linguagem somente para a parte que necessita interpretação aberta.
  4. Disponibilizar ferramentas com contratos explícitos.
  5. Adicionar persistência se existir continuidade entre interações.
  6. Utilizar n8n se houver agendamentos e integrações recorrentes.
  7. Escolher Agents SDK, ADK, Strands ou PydanticAI para agentes programáveis simples; LangGraph ou Microsoft Agent Framework para processos com estado, condições e coordenação mais complexa; CrewAI quando for pertinente investigar equipes especializadas.
  8. Acrescentar MCP quando a reutilização padronizada de ferramentas entre clientes justificar a integração.
  9. Acrescentar A2A quando houver agentes independentes e necessidade real de interoperabilidade.
  10. Validar qualidade, segurança, custos e autorização antes de conceder escrita ou execução externa.

23.2 Arquitetura mínima recomendada #

Uma aplicação acadêmica pode começar com Python + FastAPI + PostgreSQL + um conjunto pequeno de funções de negócio. O orquestrador pode ser código tradicional. Um SDK ou LLM pode ser adicionado depois. O frontend pode ser Streamlit no laboratório ou React/Next.js em uma aplicação maior; n8n é complementar quando existem eventos e integrações. Evite introduzir simultaneamente n8n, LangGraph, CrewAI, MCP, A2A e três modelos apenas porque estão disponíveis.

23.3 Projeto integrador A — Observatório de IA #

Construir uma ingestão recorrente, verificar URLs e metadados, classificar notícias, manter rastreabilidade e encaminhar casos incertos. Comparar classificação por regras, classificador convencional e LLM com/sem recuperação. Se a fonte indicar informações conflitantes, o agente deverá produzir evidências e solicitar revisão editorial. Projeto de pesquisa: impacto de ferramentas, RAG e persistência sobre completude, custo e qualidade da triagem.

23.4 Projeto integrador B — Varejo #

Construir um agente persistente de prevenção de rupturas, iniciado por eventos do PDV. Utilizar regras e previsão de demanda, registrar alertas com idempotência e preparar recomendações de compra. Evoluir para ferramentas de consulta a fornecedores e integração com orçamento, exigindo aprovação. Projeto de pesquisa: agente único versus orquestração determinística versus sistema multiagente.

23.5 Projeto integrador C — CRM e comunicação #

Construir um classificador de intenções, integrar dados sintéticos de pedidos, oferecer resposta baseada em evidência e encaminhar solicitações complexas. Comparar classificação por regras, ML e LLM; avaliar proteção de dados, tempo de resposta, escalonamento e taxa de mensagens indevidas. Contatos proativos exigem uma política de comunicação e verificações de autorização específicas do canal.

23.6 Matriz final de tecnologias #

Necessidade principal Escolha inicial razoável Quando evoluir
Tarefas repetitivas e previsíveis Python/SQL/n8n Adicionar agente se existir decisão aberta
Assistente com arquivos e aplicativos Plataforma agêntica pronta SDK próprio para controle e integrações específicas
Agente Python com poucas ferramentas Agents SDK, ADK, PydanticAI ou Strands Grafo com estado para fluxos mais complexos
Execução com ciclos, pausa e retomada LangGraph ou Microsoft Agent Framework Persistência distribuída e observabilidade
Agentes independentes de diferentes sistemas APIs ou A2A A2A se houver contratos e tarefas interoperáveis
Ferramentas reutilizáveis API → MCP quando necessário Catálogo autorizado e controle central
Procedimentos e boas práticas reutilizáveis Skills Versionamento, testes, políticas e distribuição
Conhecimento documental Recuperação lexical → RAG Vetores, reranking e avaliação de citações
Interface de agente em tempo real Web/API; AG-UI quando necessário UI declarativa com A2UI e validação
Execução corporativa gerenciada Plataforma cloud com identidade e runtime Escalar conforme SLO, segurança e custo

A decisão deve sempre incluir a alternativa mais simples como baseline, e não apenas uma comparação entre frameworks.

Matriz revisada: Necessidade × escolha × evolução.
