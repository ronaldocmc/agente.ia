Unesp.IA · Projeto pedagógico comparativo

Um problema, dez arquiteturas de agentes e automação

Para novos estudantes em orientação: use a Formação prática por tecnologia, com atribuição de uma tecnologia por aluno, testes, entregáveis e apresentação. O experimento por equipes permanece como alternativa para futuras turmas.

Um projeto de turma no qual diferentes equipes resolvem a mesma triagem institucional fictícia. Os resultados são comparados com testes, rastros de execução e uma rubrica comum, não apenas por demonstrações.

Recomendação: realize antes uma atividade-base com Python determinístico e n8n; distribua as demais tecnologias por equipe, com alternativas para laboratórios dependentes de provedores ou hardware.

Estudo de caso comum

Cenário: a secretaria recebe mensagens de estudantes e docentes para consultar inscrição, certificado, horários e situação de solicitações. Todos usam dados fictícios e a mesma API de consulta simulada.

Entradas: 20 solicitações anonimizadas e sintéticas, incluindo linguagem ambígua, informações faltantes, pedido de dado de outra pessoa, instrução maliciosa e indisponibilidade de ferramenta.

Saída contratada: JSON com categoria, resumo, ferramenta_acionada, evidencia, confianca_declarada, precisa_aprovacao e resposta. A confiança declarada não substitui avaliação objetiva.

Passo a passo para TODAS as equipes

  1. Preparação: baixar o mesmo conjunto de dados, executar o baseline Python, conferir o contrato JSON e definir os casos que exigem revisão humana.
  2. Desenhar a arquitetura: identificar interface/entrada, orquestrador, agente, LLM, ferramentas, base de dados, autorização, memória e observabilidade. Mostrar onde cada decisão ocorre.
  3. Instalar ou configurar a tecnologia atribuída: seguir a ficha e o laboratório do Agente.IA; registrar versões, dependências e custos. Não utilizar dados institucionais reais.
  4. Implementar a consulta autorizada: usar somente a ferramenta simulada consultar_solicitacao, com lista de funções permitidas e logs; bloquear alterações diretas de dados.
  5. Executar os mesmos 20 casos: registrar saída estruturada, tempo, chamadas a ferramentas, falhas e intervenção humana. Repetir três vezes quando houver comportamento probabilístico.
  6. Comparar com baseline: verificar acerto na classificação, consistência, tratamento de dados ausentes, violações de política, facilidade de manutenção e esforço de implementação.
  7. Apresentar e defender: executar uma demonstração, explicar a função da tecnologia, os limites encontrados, como foi feita a orquestração e quando NÃO a recomendariam.

Entregáveis por equipe

  • Repositório com README e instruções de instalação.
  • Diagrama de arquitetura e fluxograma de execução, identificando quem orquestra.
  • Workflow exportado ou código, configurações-modelo e dados sintéticos.
  • Arquivo CSV com os 20 cenários, resultados e critérios observados.
  • Vídeo curto de demonstração e relatório comparativo de 3–5 páginas.
  • Lista de dificuldades reais e proposta de evolução para o Escritório Virtual.

Qual LLM usar?

Na primeira rodada, fixe o LLM quando tecnicamente possível. Assim, as diferenças observadas refletem mais o orquestrador do que o modelo. Uma segunda rodada pode comparar modelos. Para execução local, Ollama é o servidor; Gemma e Llama são famílias de modelos. O Lumi é um candidato de pesquisa em português, mas suas capacidades e requisitos precisam ser verificados antes do experimento; não pressuponha suporte a tool calling. Grok Bot poderá usar modelos disponibilizados na própria plataforma, portanto a comparação deve registrar essa diferença.

Veja também Guia de modelos de linguagem e Guia de escolha tecnológica.

Como distribuir os grupos

Turma pequena: escolha cinco equipes (n8n, Agents SDK, LangGraph, Hermes e OpenClaw), mantendo Grok Bot como demonstração opcional se houver acesso. Turma maior: abra os dez grupos. Pesquisa: grupos G1 e G10 funcionam como controles; os demais investigam orquestração, persistência e colaboração.

Quando houver falta de acesso: a equipe ainda entrega análise arquitetural, skill/configuração de exemplo e testes simulados, mas deve marcar claramente “não executado em runtime real”. Isso não pode receber a mesma pontuação de execução real sem ajuste prévio da rubrica.

Evolução para nível avançado

Após a triagem, mantenha o mesmo contrato e adicione: documentos com proveniência, PostgreSQL, controle de acesso por papel, agendamento, filas, aprovação humana, persistência de sessões, auditoria e comparação de falhas. Só então componha um Escritório Virtual com vários agentes.
