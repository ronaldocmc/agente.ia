Ollama

O que é: Ollama é um runtime e servidor de inferência que permite baixar e executar determinados modelos em uma máquina própria e disponibilizá-los a aplicações por uma API local. Pode ser usado para linguagem, embeddings e ferramentas conforme o modelo e sua compatibilidade. Não é, sozinho, um agente completo: a aplicação constrói autorização, estado, loop de decisão e execução segura de ferramentas.

1. Papel arquitetural: cérebro/modelo × runtime × agente

ElementoResponsabilidade
Modelo local (por exemplo, Qwen)Produzir texto e sugerir chamada de ferramenta
OllamaServir o modelo, disponibilizar inferência e API local
Aplicação Python/SDKValidar argumentos, autenticar usuário, executar ferramentas, controlar ciclo e registrar eventos
Skill (opcional)Documentar procedimento reutilizável; não substitui autorização

2. Como começar

ollama pull qwen3
ollama run qwen3
# servidor local usual: http://localhost:11434/api

Os nomes de modelos e os requisitos de memória devem ser validados no catálogo do Ollama antes da execução. Para automação, a API HTTP suporta tool calling com modelos compatíveis; o servidor local não exige API key por padrão e não deve ser exposto publicamente sem proteção adicional.

3. Exemplos progressivos

  1. Sem agente: resumir uma notícia sintética e salvar o resultado; não há ação sobre fontes externas.
  2. Agente local: selecionar consultar_certificado, receber o retorno do backend e explicar apto/nao_apto, sem alterar a regra.
  3. Observar.IA: classificar observações coletadas e propor prioridades, mantendo validação editorial humana e fontes rastreáveis.
  4. Assistente pessoal: extrair uma intenção de lembrete e registrar apenas após confirmação do usuário.

4. Quando usar e quando não usar

Usar: laboratórios reproduzíveis, privacidade por processamento local com governança, comparação de modelos e protótipos sem custo por chamada de API. Evitar como única solução: quando o hardware disponível for insuficiente, houver exigência de desempenho que o modelo não atende ou for necessária operação gerenciada com SLA. Local não significa automaticamente privado: logs, rede, licenças, sistema e permissões ainda precisam de análise.

5. Segurança e custo

Isolar ferramentas; não executar comandos de terminal sugeridos pelo modelo sem política; validar parâmetros e identidade no backend; manter API restrita a localhost/segmento autorizado; registrar modelos e seus hashes; avaliar licenças. Custos: energia, memória, GPU/CPU, suporte, armazenamento e tempo de equipe.

6. Laboratório verificável

Agente local com Ollama e Python, com código do pacote laboratorios/lab19_independente/ollama_agente.py, baseline offline e testes de unidade.

Percurso técnico por função: Ollama

Perfil didático: Implementação prioritária. Papel: Servidor, modelos e API de inferência. Este roteiro é proposto; os testes específicos não foram executados nesta revisão.

1. Conhecer e compreender — arquitetura e responsabilidades

API local recebe prompt/mensagens e invoca modelo carregado. Se houver proposta de tool call, cliente executa função autorizada e envia retorno ao modelo; Ollama não executa automaticamente a função.

2. Comparar — critérios de seleção

llama.cpp e vLLM são alternativas de serving conforme hardware e requisitos; n8n e SDKs são consumidores da API.

3. Preparar — requisitos e limites

Instalar Ollama e selecionar modelo disponível compatível com hardware. Usar ollama list e ollama pull com tag validada, endpoint apenas local no exercício.

4–5. Preparar e implementar — atividade de aprendizagem

Experimento: Executar modelo local em API restrita e comparar chamadas de texto e tools compatíveis.

Sequência orientada: Comparar uma chamada de geração e uma chamada de ferramentas com modelo que documente suporte; medir latência e memória, registrar tag e digest quando disponível.

{"id":"REQ-001","solicitacao":"certificado","status_esperado":"apto"}

O registro acima é dado sintético de referência, não resposta obtida de um runtime. Use uma ferramenta local de consulta que aceite somente o identificador e devolva o status. O backend deve impor autorização independentemente da instrução do agente.

  1. Identifique a versão da tecnologia e o componente que será exercitado; prepare um ambiente isolado ou, para padrões e métodos, uma representação documental de teste.
  2. Execute a atividade descrita com dados sintéticos e registre entrada, configuração e saída observada.
  3. Repita com o cenário de falha da tabela abaixo; registre diferenças em vez de atribuir aprovação sem execução.

6. Testar — critérios específicos

CenárioCritério de aceitação
NominalExecutar modelo local em API restrita e comparar chamadas de texto e tools compatíveis.
Falhas e limitesValidar schema, memória, latência e ausência de tool executada sem autorização.
ReproduçãoReexecutar com mesmas versões e dados; documentar artefatos, diferenças, custo quando disponível e limitações. Repetições idênticas não são garantidas para modelos probabilísticos.

7. Aplicar — integração com o Agente.IA

Use a atividade como componente de uma solução de consulta, coleta, curadoria ou avaliação, conforme seu papel. Vincule a execução à tarefa, à tecnologia e ao resultado; não atribua ao componente funções que ele não implementa.

8. Evoluir — próximos passos

Adicionar persistência, ferramentas, delegação ou rotinas uma por vez; comparar cada evolução com a implementação mínima e registrar a diferença de custo, qualidade e segurança.
